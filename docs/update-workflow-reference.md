# Как обновление пакета доходит до принятой ветки

[Проект Standard v0.2](../STANDARD.md) задаёт требования к проверкам и
публикации. Это руководство показывает, как пройти тот же путь в
конкретном оверлее. Стадии обозначают решения и границы прав. Discover,
Prepare, Validate и Handoff могут выполняться в одном задании с правами
чтения. Количество файлов, jobs и скриптов определяет проект. Право
автоматической записи в удалённый репозиторий появляется только в Publish.

## Что меняется от профиля к профилю

| Профиль | Откуда берётся версия и как она попадает на ревью |
| --- | --- |
| Manual | Сопровождающий выбирает источник, готовит diff и проводит применимые проверки до принятия. Workflow обновления и автоматический Publish необязательны. При автоматизации отдельных частей действуют соответствующие гарантии. |
| Release | Автоматизация выбирает допустимый upstream-релиз и связывает версию, тег, неизменяемый идентификатор и скачанные байты по R1. |
| Snapshot | Источник — полный SHA коммита. Версию, URL источника и, где применимо, связанные компоненты определяют по данным этого снимка. Если локальная политика требует согласованной пары, её проверяют вместе по R2. |
| Extended Release | Путь Release с дополнительным правилом R3 при отдельной публикации distfiles. До Draft PR проверяют идентичность и доступность новых или переиспользованных файлов. При частичном сбое отдельно проверяют состояние этих файлов. |

Для ручного обновления первые три стадии служат ориентиром для работы с
локальным кандидатом. Доказательства и порядок принятия определяют
применимые требования проверки и защиты ветки. Далее приведён условный
автоматизированный пример Release.

## Пример обновления с 1.4.0 до 1.5.0

В оверлее есть `app-misc/example-1.4.0` и предыдущая версия
`1.3.0`. Оверлей хранит две версии для отката. База — точный коммит
принятой ветки, от которого началось обновление. Кандидат — изменения
файлов на этой базе вместе с относящимися к ним источниками.

### Discover — выбрать источник

Сопоставьте принятую версию и правила отбора с тем, что опубликовал
upstream. Это позволяет отличить отсутствие работы от сбоя поиска.
Прочитайте состояние веток или PR, если оно влияет на отбор. В примере
допустимый стабильный релиз `v1.5.0` разрешается в полный SHA.
Успешный поиск даёт выбранный источник и базу. При остановке
сообщите её причину.
Новый релиз ещё не готов к публикации. Запросы идут на чтение, а отчёт
может сохраняться локально. Уже упакованная версия означает отсутствие
обновления, открытый конфликтующий PR может вызвать штатный пропуск,
изменение упаковки может потребовать решения человека, а неверный тег
или ошибка чтения блокируют допуск. [Исходы Discover](../STANDARD.md#a1-discover)

### Prepare — собрать изменения на фиксированной базе

Возьмите найденный релиз, его неизменяемый идентификатор и базу.
Подготовьте изменения в изолированной рабочей копии, чтобы не затронуть
принятое дерево. В примере добавьте ebuild `1.5.0`, сохраните
`1.4.0` для отката, уберите `1.3.0` и подготовьте связанные изменения
Manifest и документации. Результат — определённый diff или
воспроизводимый план с файлами, нужными для проверок. Допустимы локальные
файлы и скачивание источников. Несовместимая структура, недопустимое
состояние версий или обязательное ручное ревью останавливают допуск.

### Validate — проверить итоговое содержимое

Возьмите подготовленные файлы, базу и список обязательных проверок до
публикации. Свяжите скачанные байты с выбранным источником, проверьте
Manifest и метаданные средствами Gentoo. В примере контрольные суммы
архива `1.5.0` должны совпасть с записью в итоговом Manifest.
Проверки могут оставить локальные логи и Manifest во временной копии.
Результат — доказательства для точных байтов кандидата и окружения.
Несовпадение источников, ошибки метаданных или отсутствие успешного
результата обязательного шага блокируют публикацию. Обычный CI,
resolver, сборка и runtime дают разные доказательства.
[Матрица проверок](../STANDARD.md#проверки-и-доказательства)

### Handoff — передать файлы вместе с результатами

Возьмите кандидата, прошедшего предпубликационные проверки. Свяжите
передаваемые файлы или воспроизводимый план с полным SHA базы,
происхождением источника (provenance), составом и доказательствами.
В примере получатель сверяет связь ebuild и Manifest для `1.5.0`
с проверенным архивом и той же базой. Это защищает от
смешивания запусков и подмены файлов. CI может сохранить артефакт и
логи. Перед записью получатель проверяет handoff по правилам из
доверенной ревизии. Неверная база, нарушенная целостность, посторонние
пути или изменения приводят к отказу.

### Publish — выставить проверенный diff

Входом служит проверенный handoff. Перед первой записью сверьте
разрешённые репозиторий и ref, текущий SHA удалённой целевой ветки,
итоговый diff и конфликты веток и PR. Это позволяет заметить изменения,
появившиеся за время подготовки. Для `1.5.0` результатом будут ветка
кандидата и Draft PR в разрешённую целевую ветку. Устаревшая база,
конфликт или dry-run блокируют запись. Если push состоялся, а PR
открыть не удалось, ветка может остаться. Отчёт должен помочь определить
последний подтверждённый шаг и остаточное состояние перед повторами.
[Требования к публикации](../STANDARD.md#handoff-и-публикация)

### Accept — принять изменение вручную

Владелец берёт точный PR head и целевую ветку, сверяет diff, обязательные
checks и применимые сценарии. Например, на Gentoo он проверяет план
установки `1.5.0` из копии кандидата. Запуск resolver показывает выбор
пакета и зависимости. Установка и проверка работы приложения выполняются
отдельно, если их требует политика. Владелец вручную сливает проверенный
PR или оставляет его на доработку. Merge меняет принятое состояние.
При новом head нужны доказательства для нового содержимого, а пропуск
проверки или неподтверждённый обязательный сценарий останавливает
принятие.

## Пример Noctalia

На ревизии `45706256dc877fc13e76b0019fb6081dcd07c2fc` Noctalia
показывает один способ реализовать профиль Release. Читайте
[пользовательский README][noctalia-readme] для установки и отката,
[руководство по автоматизации][noctalia-automation] для пути кандидата
и [справочник CI и безопасности][noctalia-ci] для проверок, настроек
и восстановления.

- **От релиза к ротации.** Watcher проверяет допустимость релиза, SHA
  тега и `VERSION` на этом SHA. Из имён ebuild берутся текущая и
  резервная версии. Ротация возвращает `up-to-date`, если обновление
  не требуется, `dry-run`, если построен только план, или `prepared`,
  если применена ротация с обновлением двух README. Watcher отдельно
  различает `up-to-date`, `already-reported`, `dry-run` и
  `release-available`. Dry-run с подходящим релизом готовит временную
  копию и план без изменения файлов пакета. После успешного поиска и
  проверки допуска запускаются unit-тесты. Проверка архива, Gentoo,
  загрузка handoff и Publish в dry-run пропускаются.
  [Workflow][noctalia-workflow] · [Watcher][noctalia-watch] · [Ротация][noctalia-prepare]
- **Архив, Manifest и кандидат.** Prepare сверяет `SRC_URI`,
  скачивает канонический архив GitHub по HTTPS, читает его целиком и
  сверяет метаданные Git tar и PAX с SHA из Discover. Эта проверка
  опирается на сервис архивов GitHub и метаданные, без самостоятельной
  реконструкции Git tree. Portage генерирует Manifest из скачанного
  файла. После `pkgcheck` скрипт повторно сверяет размер и хеши архива
  со строкой `DIST` кандидата, а строку резервной версии — с базой.
  Handoff связывает эту проверку с составом файлов кандидата.
  [Workflow][noctalia-workflow] · [Код проверок][noctalia-handoff]
- **Handoff и Publish.** Read-only Prepare загружает handoff после
  проверки кандидата и записывает readiness с идентификатором и
  digest артефакта. Отдельный Publish проверяет контекст, ZIP, базу
  и ожидаемые изменения, формирует точный коммит и выполняет записи
  через свою точку входа. Опция `--pull-request-request` и промежуточный
  JSON запроса PR удалены. Запрос собирается в Publish.
  [Workflow][noctalia-workflow] · [Handoff][noctalia-handoff] · [Publish][noctalia-publish]
- **Create-only publication.** Перед push Noctalia проверяет
  конфликтующий открытый PR, историю PR для точной ветки, отсутствие
  ветки и SHA удалённой `main`. Пустое ожидаемое значение в
  `--force-with-lease=<ref>:` разрешает создать только отсутствующий
  ref. Подтверждением является ответ Git `[new branch]`. Перед
  Draft PR повторно сверяются конфликты и удалённая база, а head
  ветки должен быть равен подготовленному коммиту. Остаточная ветка
  блокирует автоматический повтор и требует решения владельца.
  [Publish][noctalia-publish] · [Восстановление][noctalia-ci]

Ротация двух версий, формат handoff и политика create-only принадлежат
Noctalia. Другие реализации могут выбирать свои схемы в пределах
действующих требований. История запусков и границы доказательств
описаны в [состоянии пилота](adoption-history.md#пилот-noctalia).
