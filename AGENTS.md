# Правила работы с Gentoo Overlay Standard

## Область работы

- Сверяйтесь с [README.md](README.md) и [базовым аудитом](audits/baseline.md)
  перед изменениями. Начало следующей фазы требует отдельного решения владельца.
- Оверлеи остаются независимыми. Сохраняйте ограничения пакетов, правила
  совместимости и отката, а также существующие границы доступа и публикации.
- В Phase 0 разрешено менять только `README.md`, `AGENTS.md` и
  `audits/baseline.md` в этом репозитории. Читайте исходники оверлеев без
  изменений. Запрещены правки ebuild, Manifest, скриптов, workflows и
  настроек GitHub, запуск workflows, сборка и установка пакетов, создание
  веток, коммитов, push и PR в оверлеях. Архивные оверлеи исключены из миграции.
- Общие runtime-зависимости, reusable workflows, общие Python-пакеты,
  генераторы, submodules и синхронизация выходят за пределы Phase 0.

## Доказательства

- Зафиксируйте исходное состояние Git. Для каждого оверлея подтвердите URL,
  доступность, ветку по умолчанию, статус архивации, полный SHA и время
  проверки через GitHub. Читайте только файлы этого коммита. Сверяйте
  локальную копию с удалённым SHA или используйте временную копию вне
  рабочих деревьев.
- Привязывайте факты об исходниках к путям на точной ревизии. Для настроек
  и запусков приводите прямые ссылки и дату наблюдения. Помечайте недоступные сведения как
  UNKNOWN. Не извлекайте секреты и не запрашивайте их значения.
- Различайте реализованные проверки, подтверждённые результаты запусков,
  сведения из документации, выводы и предложения. Указывайте версию
  пакета, ревизию и проверенный сценарий там, где они определяют границы
  доказательства. Успешный workflow с пропущенным заданием не подтверждает
  результат этого задания.
- Сравнивайте контракты и последствия отказов. Для DRIFT укажите, какое
  действующее соглашение или описание расходится с реализацией. Для
  BLOCKER, SECURITY и CONFLICT приводите подтверждённое последствие или
  несовместимость. Обоснованные различия сохраняйте.

## Проверка и принятие

1. Проверьте охват репозиториев, точность ревизий и ссылок, границы аудита
   и список изменённых файлов. Выполните `git diff --check`. Для новых
   неотслеживаемых файлов дополнительно сравните каждый с `/dev/null` через
   `git diff --no-index --check`.
2. Подготовьте отчёт с наблюдаемыми результатами, открытыми вопросами и
   предлагаемым объёмом следующей фазы. Оставьте файлы без коммита для ревью.
3. Владелец принимает результаты аудита, утверждает объём следующей фазы
   и вручную принимает изменения в оверлеях. Предложение в аудите не даёт
   разрешения на публикацию, миграцию или merge.
