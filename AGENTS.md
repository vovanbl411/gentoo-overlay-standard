# Правила работы с Gentoo Overlay Standard

## Область работы

- Сверяйтесь с [README.md](README.md), [принятым стандартом](STANDARD.md)
  и [базовым аудитом](audits/baseline.md). `STANDARD.md` — единственный
  источник общих требований. Политику упаковки и принятое состояние
  определяет соответствующий оверлей.
- Phase 0 и Phase 1 завершены. Standard v0.1 принят на ревизии
  `becf8221ff745d722eb74c0e91435088c40b9ac7`. Phase 2 ограничена
  справочными шаблонами, чек-листом и точечной проверкой раскладки тестов.
  Исторический аудит сохраняйте. В стандарте разрешены запись о принятии
  и подтверждённая необязательная рекомендация по раскладке тестов.
- Читайте исходники оверлеев по аудированным SHA. Эксперимент проводите
  на временных копиях. Запрещены изменения оверлеев и настроек GitHub,
  запуск workflows, сборка пакетов и внедрение шаблонов в оверлеях.
  Для эксперимента допустимы одноразовые контейнеры с нужными
  инструментами проверки. Конфигурацию хоста сохраняйте.
- Используйте существующие решения как образцы. Шаблоны не добавляют
  нормативных требований и не вводят общий код или общую инфраструктуру
  исполнения. Архивные оверлеи исключены из внедрения.

## Доказательства

- Зафиксируйте исходное состояние Git и сверьте принятый коммит Phase 0.
  Используйте аудит как историческое свидетельство. При существенном
  вопросе читайте только нужные файлы по аудированному SHA. Сохраняйте
  исторические ревизии и остальные результаты аудита.
- Привязывайте факты об исходниках к путям на точной ревизии. Для настроек
  и запусков приводите прямые ссылки и дату наблюдения. Помечайте недоступные
  сведения как UNKNOWN. Не извлекайте секреты и не запрашивайте их значения.
- Различайте реализованные проверки, подтверждённые результаты запусков,
  сведения из документации, выводы и предложения. Указывайте версию
  пакета, ревизию и проверенный сценарий там, где они определяют границы
  доказательства. Успешный workflow с пропущенным заданием не подтверждает
  результат этого задания.
- Сравнивайте контракты и последствия отказов. Для DRIFT укажите, какое
  действующее соглашение или описание расходится с реализацией. Различия
  с проектом стандарта учитывайте как возможные работы при внедрении.
  Для BLOCKER, SECURITY и CONFLICT приводите подтверждённое последствие
  или несовместимость. Обоснованные различия сохраняйте.

## Проверка и принятие

1. Сверьте шаблоны и чек-лист с принятой версией стандарта. Укажите
   аудированные источники, результаты точечных проверок и их ограничения.
2. Проверьте ревизии, Markdown-ссылки, список изменений и
   `git diff --check`. Для новых неотслеживаемых файлов дополнительно
   сравните каждый с `/dev/null` через `git diff --no-index --check`.
3. Оставьте изменения без коммита для ревью. Владелец отдельно разрешает
   следующую фазу и принимает решение о внедрении для каждого оверлея.
