# Gentoo Overlay Standard v0.2

**Статус — действующая версия, принятая владельцем.** Ранее действовал
[Standard v0.1](https://github.com/vovanbl411/gentoo-overlay-standard/blob/becf8221ff745d722eb74c0e91435088c40b9ac7/STANDARD.md).
[Предыдущий проект v0.2](https://github.com/vovanbl411/gentoo-overlay-standard/blob/b90ec059d72fd5d55e9b0f1e47ba11acac7089b0/STANDARD.md)
сохраняет исходную формулировку для сверки.

## Область и термины

Стандарт задаёт общие инженерные гарантии для активных Gentoo-оверлеев
`vovanbl411`. Этот репозиторий хранит общие требования. Каждый оверлей
остаётся независимым и определяет свою политику упаковки и принятое
состояние. Vicinae и Spotify Player архивированы и исключены из внедрения.

- **MUST** — обязательное требование. Для каждого ID указаны
  применимость, основание и критерий выполнения.
- **SHOULD** — предпочтительная практика. Допустима обоснованная альтернатива.
- **MAY** — необязательная возможность.

**Upstream** — исходный проект пакета. **Distfiles** — скачиваемые файлы
пакета. **Manifest** хранит контрольные суммы применимых файлов.
**Provenance** связывает проверенные байты с источником, например
с конкретным релизом или коммитом.

**База** — точный коммит целевой ветки оверлея, от которого подготовлено
обновление. **Кандидат** — набор изменений и относящихся к ним источников
и distfiles, однозначно определённый для этой базы. **Принятое состояние**
— состояние целевой ветки после решения владельца. **Handoff** — передача
проверенного кандидата и доказательств в контур публикации.

**PR (pull request)** — запрос на слияние изменений. **Draft PR** —
черновик для ревью. **Assets** здесь — отдельно публикуемые файлы,
которые нужны кандидату. **Required check** — проверка с определённым
именем и источником, которую GitHub требует для слияния.

## Самостоятельность оверлея и принятие стандарта

У оверлея есть собственные правила и ответственность за сопровождение.
Отдельное решение владельца связывает выбранную версию стандарта с
доказательствами на конкретной ревизии.

### S1

**Применимость.** Все

**Зачем.** Изоляция сопровождения и отказов.

**MUST.** Сохранять самостоятельное сопровождение оверлея. Общие
runtime-зависимости между оверлеями, reusable workflows, общие Python-пакеты,
генераторы, submodules и автоматическая синхронизация исключены из архитектуры
стандарта.

**Критерий.** Документация и проверки оверлея работают по его собственному
контракту. Внедрение не добавляет перечисленных связей. Существующие зависимости
пакетов рассматриваются по локальной политике.

### S2

**Применимость.** Все

**Зачем.** Явный переход на новые требования.

**MUST.** Внедрять конкретную версию стандарта отдельным решением владельца по
каждому оверлею.

**Критерий.** В оверлее или решении о внедрении зафиксированы версия, профиль,
проверенные требования, доказательства, применимые исключения и решение
владельца. До внедрения расхождения с проектом стандарта учитываются как будущие
работы или вопросы.

### S3

**Применимость.** Все

**Зачем.** Сопровождающий может самостоятельно проверять и менять проект.

**MUST.** Обеспечить человеческую сопровождаемость. Реализация и понятная
документация должны позволять сопровождающему понять основное поведение проекта,
воспроизвести проверки, локализовать ошибку и осознанно вносить изменения.
Предпочтительна наиболее простая достаточная реализация, сохраняющая применимые
инженерные гарантии.

**Критерий.** По коду и документации сопровождающий может проследить основной
путь до результата, воспроизвести применимые проверки и определить, где и почему
выполнение остановилось. При ревью используются приведённые ниже критерии.

### Ревью сопровождаемости

Сопровождаемость оценивают наряду с корректностью, соответствием объёму
задачи, риском регрессий и безопасностью.

- В автоматизированном процессе основная последовательность действий
  видна из workflow и точек входа скриптов. По именам функций, аргументов
  и переменных понятно их назначение. Видно, за что отвечают компоненты
  и как они взаимодействуют.
- Подтверждённо ненужный код в рабочей реализации удаляют. У сохранённых
  устаревших интерфейсов и повторения логики есть обоснование. Константы
  выражают осознанную политику, фиксируют зависимости или ограничивают
  допустимое поведение. Текущие версии пакетов и состояние берут из
  принятого источника истины, когда их можно получить оттуда.
- У сложных проверок есть конкретное назначение, которое можно объяснить
  сопровождающему. Новые абстракции, зависимости, слои конфигурации и
  автоматизацию вводят при подтверждённой необходимости.
- Сообщения об ошибках и остановках помогают определить, на каком шаге и
  по какой причине выполнение прекратилось.

Обоснованную сложность сохраняют. Подтверждённо лишнюю сложность,
неиспользуемый код, хрупкие предположения и необоснованное дублирование
рассматривают по их конкретным последствиям. Стилистическое предпочтение
само по себе не основание для замечания. Количество строк, функций, файлов
или тестов само по себе не показывает качество. Форму скриптов и
архитектуру определяет проект. Требование рефакторинга опирается на
конкретную проблему. При упрощении сохраняют применимые инженерные гарантии.

## Профили

Все профили наследуют общие правила. Дополнительные требования
автоматизации действуют для автоматизированных кандидатов. На пакеты,
которые обновляются вручную, распространяются общие правила.

| Профиль | Дополнение к общим правилам |
| --- | --- |
| Manual | Ручной путь от источника до принятия. Автоматизация обновления и публикации необязательна. При её добавлении применяются соответствующие гарантии стадий и публикации. |
| Release | Автоматизированный кандидат из релиза по R1. Отбор stable-релизов и правила версионирования задаёт оверлей. |
| Snapshot | Автоматизированный кандидат из снимка по R2. Согласованность нескольких пакетов проверяется там, где она входит в локальную политику. |
| Extended Release | Наследует Release. При отдельной дистрибуции distfiles применяется R3. |

### Источники кандидата

Профиль определяет, к какому источнику привязывают версию и какие
доказательства нужны, чтобы повторить этот выбор.

#### R1

**Применимость.** Release и Extended Release

**Зачем.** Тег и загруженный архив могут расходиться.

**MUST.** Связать версию кандидата с допустимым upstream-релизом и проверенным
источником по локальной политике provenance.

**Критерий.** По доказательствам воспроизводится соответствие версии,
release/tag, разрешённого commit или другого неизменяемого идентификатора и
проверенных байтов. Несовпадение блокирует допуск.

#### R2

**Применимость.** Snapshot

**Зачем.** Ветка меняется, компоненты могут стать несовместимыми.

**MUST.** Связать версию с полным upstream commit SHA и проверить происхождение
связанных компонентов, если они входят в снимок.

**Критерий.** Версия и `SRC_URI` воспроизводятся из зафиксированных входов. Если
версия выводится из commit timestamp, файла версии или lock, используются данные
того же коммита. Если политика требует согласованной пары или прямого
продвижения истории, проверяется и этот инвариант.

#### R3

**Применимость.** Extended Release, если публикуются отдельные distfiles

**Зачем.** Distfile может остаться после сбоя PR или иметь другие байты.

**MUST.** Связать assets с кандидатом и Manifest, проверить повторное
использование и определить порядок публикации и восстановления при частичном
сбое.

**Критерий.** Новый или переиспользуемый asset проверяется по идентичности и
целостности. Публикация останавливается при конфликте. До открытия Draft PR
подтверждена доступность требуемых assets. Инструкция покрывает сбой между
публикацией assets и PR.

## Структура и документация

Структура дерева позволяет Portage прочитать пакеты. Документация
помогает пользователю подключить оверлей, а сопровождающему — повторить
проверки и понять правила изменений.

### D1

**Применимость.** Все

**Зачем.** Portage должен распознавать оверлей и проверять источники.

**MUST.** Хранить ebuild в `<category>/<package>/`, package-файлы в
соответствующем пакете, описывать пакет в `metadata.xml` и поддерживать
применимый Manifest. Согласовать `metadata/layout.conf` и `profiles/repo_name` с
фактической конфигурацией.

**Критерий.** Gentoo-инструменты читают дерево с объявленными masters и
согласованным именем. Package metadata валидны, Manifest соответствует политике
и distfiles. При thin Manifest и отсутствии distfiles Manifest может
отсутствовать.

### D2

**Применимость.** Все, дополнительно для существующих тестов

**Зачем.** Установка и проверка должны быть воспроизводимы.

**MUST.** Описать применимые разделы README и дать воспроизводимую команду для
имеющихся тестов с рабочей директорией и предпосылками. Согласовывать факты и
инструкции в поддерживаемых локализациях.

**Критерий.** Ревью подтверждает перечисленные ниже сведения, доступность ссылок
и совпадение версий, инструкций и ограничений между языками. У команды тестов
указаны условия запуска и область проверки.

### D3

**Применимость.** Все

**Зачем.** Сопровождающий должен видеть границы изменений и принятия.

**MUST.** Указать в `AGENTS.md` область проекта, источники истины, принятую
политику упаковки, допустимые изменения, требования к проверке и порядок
принятия владельцем. Допустимы точные ссылки на действующую документацию.

**Критерий.** По файлу и его локальным ссылкам можно определить все шесть
пунктов.

### D4

**Применимость.** Где инструменты создают локальные служебные файлы и их можно
случайно добавить в Git

**Зачем.** Избежать попадания кэшей, сборочных остатков и локальных настроек в
коммит.

**MUST.** Исключить такие файлы через `.gitignore` или уже действующий
эквивалент.

**Критерий.** Типовые генерируемые пути исключены, а принятому состоянию,
distfiles-метаданным и другим намеренно отслеживаемым файлам игнорирование не
мешает.

**README.** D2 охватывает назначение, пакеты, подключение и синхронизацию
оверлея, установку пакетов, USE-флаги и требования, статус проверок и их
ограничения, обновление и откат, сопровождение и автоматизацию, ссылки
на дополнительные материалы. Достаточно короткого указания, если
поддерживаемого сценария пока нет, например отката при единственном ebuild.
Русский язык SHOULD быть основным, английская версия SHOULD быть
доступна. Заголовки и объём зависят от проекта.

**Документация для человека.** По S3 сопровождающему должны быть понятны
контракт компонента и причины выбора реализации. Начните с задачи
компонента и объясните, зачем он нужен. Затем опишите входные данные,
действия, результат и побочные эффекты. Завершите объяснением того, что
происходит при ошибке и как воспроизвести или проверить поведение.

Для автоматизированного проекта опишите основной путь от workflow через
точки входа скриптов до результата. Используйте простые объяснения,
конкретные примеры, ссылки на исходники, небольшие схемы и команды там,
где они помогают проследить этот путь. Для команд поясняйте назначение,
существенные аргументы, ожидаемый результат и побочные эффекты.

README ориентирован прежде всего на пользователя оверлея. Документация
автоматизации предназначена для сопровождающего. `AGENTS.md` содержит
правила работы агента и может ссылаться на инструкции для человека.
Исторические данные, аудиты, промежуточные отчёты и результаты миграций
хранятся отдельно от действующих инструкций. README и эксплуатационные
руководства описывают действующее поведение. Размещение этих сведений
зависит от проекта. Описание нескольких стадий или функций может
находиться в одном месте.

**Файлы сопровождения.** Скрипты SHOULD храниться в `scripts/`. Рабочие
имена GitHub workflows для CI и подготовки обновления SHOULD быть
`ci.yml` и `prepare-update.yml` при выборе новых имён. Существующие имена
допустимы. При переименовании действует G2. Документация в `docs/`,
состояние в `automation/` и локальный task runner MAY использоваться по
потребностям проекта. Для новых наборов тестов SHOULD использоваться
`scripts/tests/`. Существующие раскладки допустимы с документированной
командой запуска и областью проверки.

## Стадии автоматизации

Стадии описывают путь от поиска обновления до решения владельца.
**Readiness** означает готовность конкретного кандидата к публикации
после обязательных предпубликационных проверок.

A1–A6 задают MUST для автоматизированного обновления. Для ручного потока
применяются общие требования, в том числе V1, V2 и G1. Стадии можно
объединять, если сохраняются границы прав и изоляции по P1. Число скриптов
и формат обмена определяет оверлей.

### A1 Discover

**Зачем.** Различать отсутствие обновления и отказ проверки.

**MUST.** Сопоставить принятое состояние на известной базе, upstream и правила
отбора. Прочитать применимое PR/branch-состояние, если оно влияет на отбор.

**Результат и критерий.** Выдать различимый исход из перечня ниже. Допустимы
запросы на чтение и локальный отчёт. При неопределённости или сбое готовность к
публикации отсутствует.

### A2 Prepare

**Зачем.** Получить изолированный кандидат с допустимым набором изменений.

**MUST.** Взять `CANDIDATE`, зафиксированные базу и upstream identity.
Подготовить ebuild, Manifest и применимые package-файлы по локальной политике.

**Результат и критерий.** Получить идентифицируемый diff или воспроизводимый
план с нужными файлами. Допустимы локальная рабочая копия, временные файлы и
скачивание источников. Ошибка или обязательное ручное ревью блокируют допуск.

### A3 Validate

**Зачем.** Привязать успешные проверки к конкретному содержимому.

**MUST.** Получить подготовленный кандидат, базу и применимые проверки из V1.
Проверить источники, Gentoo metadata и остальные обязательные для этого
кандидата категории.

**Результат и критерий.** Зафиксировать результаты по V2. Разрешены
изолированный контейнер, локальная генерация Manifest и логи. Доказательства
относятся к итоговым байтам кандидата. Ошибка или отсутствие успешного
результата обязательной проверки блокируют допуск.

### A4 Handoff

**Зачем.** Исключить подмену и применение к неверной базе.

**MUST.** Передать только кандидат с успешными проверками, обязательными до
публикации. Состав, связывание доказательств и проверка при приёме определены в
H1–H2.

**Результат и критерий.** Получить проверенный handoff либо отказ без перехода к
записи. Допустима передача артефактов и логов средствами CI.

### A5 Publish

**Зачем.** Выставить проверенный diff на ревью с контролем удалённого состояния.

**MUST.** Принять проверенный handoff, подтвердить цель, свежесть базы,
разрешённые изменения и отсутствие блокирующего конфликта по P1–P4.

**Результат и критерий.** Допустимы только проектные операции публикации,
включая ветку кандидата, Draft PR и, где применимо, проверенные assets по R3.
При сбое сообщить результат и остаточное состояние по P4.

### A6 Accept

**Зачем.** Сохранить решение о принятом состоянии за владельцем.

**MUST.** Владелец сверяет точный PR head и целевую ветку, просмотренный diff,
обязательные проверки и сценарии приёмки по V1 и G1.

**Результат и критерий.** Владелец вручную обновляет принятое состояние через
merge либо оставляет кандидата на доработку или отклоняет его. Успешная
публикация сама по себе не меняет принятое состояние.

| Исход Discover | Семантика |
| --- | --- |
| `NO_UPDATE` | По правилам отбора нового кандидата нет. |
| `CANDIDATE` | Найден обновляемый релиз или снимок, известны его источник и база. Допуск возможен только после проверок. |
| `SKIPPED` | Штатный пропуск по известной причине, например при открытом automation PR. |
| `REVIEW_REQUIRED` | Для продолжения нужно ручное решение, например при изменении upstream packaging. |
| `ERROR` | Проверка не завершилась или её результат недостоверен. |

Имена исходов описывают смысл. Реализация MAY выражать его через
существующие outputs, логи, коды возврата или другие форматы.

## Handoff и публикация

Handoff связывает файлы с доказательствами. Перед записью Publish
проверяет эту связь и заново читает удалённое состояние, которое могло
измениться за время подготовки.

### H1

**Применимость.** Автоматизированный handoff

**Зачем.** Предотвращает смешивание результатов разных запусков.

**MUST.** Связать артефакт или воспроизводимый план с полным SHA базы,
идентичностью кандидата, upstream provenance, составом и доказательствами
validation.

**Критерий.** Получатель однозначно определяет ожидаемый артефакт, запуск или
попытку, состав и кандидата. Изменённые файлы, Manifest и проектное состояние
связаны с проверками через проверяемую целостность или воспроизведение.

### H2

**Применимость.** Приём handoff перед записью

**Зачем.** Артефакт не должен управлять привилегированными действиями.

**MUST.** Проверять полученное по правилам из доверенной ревизии. Сверять
идентичность, целостность, разрешённые типы и пути, локальное package state и
итоговый diff с разрешёнными операциями.

**Критерий.** Подмена артефакта, неожиданный файл, ссылка или выход за
разрешённый путь, неверный base или package state приводят к отказу до удалённой
записи. Переданные файлы не исполняются как код публикации.

### P1

**Применимость.** GitHub Actions и автоматическая публикация, по применимости

**Зачем.** Ограничивает последствия ошибки или подмены в проверяемом коде.

**MUST.** Выдать jobs минимально необходимые полномочия. Discover, Prepare,
Validate и передача handoff не могут писать в удалённое состояние репозитория.
Закрепить внешние Actions полным SHA и отключить сохранение checkout
credentials, кроме отдельно обоснованного случая.

**Критерий.** Сверены workflow/job permissions, токены и настройки checkout. До
Publish нет credentials с правом записи в repo. Внешние `uses` указывают полный
commit SHA. Случай сохранения credentials имеет конкретное назначение и
согласованные границы.

### P2

**Применимость.** Автоматический Publish

**Зачем.** Не допустить публикацию в fork, из недопустимого ref или с устаревшей
базы.

**MUST.** Явно ограничить репозиторий и целевую ветку, допускать только
прошедший применимые предпубликационные проверки кандидат вне dry-run. Перед
первой удалённой записью проверить текущий remote base по SHA handoff.

**Критерий.** Правило допуска фиксирует разрешённые repo и целевой ref и
ограничивает ref запуска, где он управляет кодом публикации. Чужая цель, stale
base, отсутствующая проверка и dry-run исключают push, запись PR, release и
assets.

### P3

**Применимость.** Автоматический Publish

**Зачем.** Проверка и запись могут конкурировать с другим запуском или
человеком.

**MUST.** Проверять конфликтующие PR и ветки до записи. При изменившемся
состоянии прекращать запись или применять документированное ограниченное
восстановление.

**Критерий.** Сценарии открытого PR, остаточной ветки и изменившегося remote ref
имеют определённый исход. Неизвестное или чужое состояние блокирует запись.
Переиспользование требует подтверждения эквивалентности, а обновление ветки —
проверки принадлежности, ожидаемого ref и защиты от параллельной перезаписи.

### P4

**Применимость.** Автоматический Publish

**Зачем.** Владелец получает проверяемый diff и контролирует принятие.

**MUST.** Публиковать через Draft PR, без auto-merge. Документировать обработку
частичного сбоя.

**Критерий.** Предусмотрены отдельная ветка, Draft PR на разрешённую base и
ручной merge. После неполной публикации видны последний завершённый шаг,
оставшиеся ветка/PR/assets и безопасное действие при повторе или ручном
восстановлении.

Формат, состав и механизм проверки handoff выбирает оверлей. Допустимы
проверенный набор файлов, повторное построение из доверенной базы или их
сочетание. Конкретный способ восстановления остаётся локальным.

## Проверки и доказательства

Проверка метаданных, проверка зависимостей и работа пакета в сеансе
отвечают на разные вопросы. **Resolver** — механизм Portage, который
строит план установки с учётом зависимостей, профиля и USE-флагов.

### V1

**Применимость.** Все, по матрице ниже

**Зачем.** Проверки отвечают на разные вопросы и имеют разную стоимость. CI
выявляет регрессии автоматизации в PR и принятой ветке.

**MUST.** Определить применимые категории и момент выполнения. До Publish
успешно пройти проверки, требуемые к этой стадии. До Accept пройти оставшиеся
проверки, требуемые к принятию. Для автоматизированных оверлеев обеспечить
Repository CI по матрице.

**Критерий.** Для кандидата видны обязательные проверки до публикации и до
принятия. Для условных категорий указаны применимость, локальный сценарий или
обоснование неприменимости. Для автоматизированных оверлеев конфигурация и
результаты CI подтверждают запуск для PR и при изменениях принятой ветки,
включая фактическое выполнение применимых unit-тестов автоматизации.

### V2

**Применимость.** Все, при указании результатов или принятии решения

**Зачем.** Статус запуска не показывает, какие шаги реально выполнены.

**MUST.** Привязать каждое доказательство к ревизии оверлея, кандидату,
окружению, команде или механизму, объёму и ограничениям проверки и её
результату.

**Критерий.** Результаты можно сопоставить с конкретным кандидатом и проверкой.
Если детали исторической проверки недоступны, пробелы видны и не закрывают
обязательный gate.

| Категория | Manual | Release, Snapshot, Extended Release |
| --- | --- | --- |
| Repository CI | SHOULD для повторяемых проверок, если есть потребность. Автоматизированный CI необязателен, допустима ручная проверка. | MUST запускать CI для PR в принятую ветку и при изменениях этой ветки. CI выполняет применимые unit-тесты автоматизации и определённые проектом проверки репозитория, обязательные до Accept по V1. Дорогие сборки пакетов выполняются по локальной политике. |
| Целостность и provenance источников | MUST при изменении источников до Accept по V1. | MUST для автоматизированного кандидата до Publish по V1, включая distfiles кандидата и используемые проектом связанные компоненты. |
| Gentoo metadata и Manifest | MUST проверить применимые изменения упаковки до Accept по V1. | MUST проверить Gentoo-инструментами metadata и применимый Manifest кандидата до Publish по V1. |
| Dependency resolver | По локальной политике при изменении зависимостей, USE или совместимости. | По локальной политике. В Snapshot проверка учитывает связанную пару, если её требует политика. |
| Package preparation | По локальной политике, например для применения patch или подготовки исходников. | По локальной политике. |
| Полная сборка | По локальной политике, для заявленной конфигурации. | По локальной политике, для заявленной конфигурации. |
| Runtime | По локальной политике и доступному окружению. | По локальной политике, включая аппаратные или сеансовые сценарии там, где они существенны. |
| Owner acceptance | MUST до изменения принятого состояния по G1. | MUST до изменения принятого состояния по G1 и A6. |

Отчёт различает `passed`, `failed`, `skipped` (шаг условно пропущен),
`not run` (проверку не запускали), `not applicable` (проверка
неприменима) и `unknown` (результат неизвестен). Успех workflow
не подтверждает пропущенный шаг. Metadata, resolver и `ebuild prepare`
подтверждают только свои стадии. Сведения из README или checkpoint
помечаются как документированные. Для правок только документации стандарт
не требует сборки. Если меняется команда сборки или утверждение о
совместимости, проверяется конкретное изменение.

`pkgcheck`, Portage Manifest и `emerge -pv` SHOULD использоваться там,
где отвечают на вопрос проверки. Область сканирования, Gentoo tree,
профиль, архитектура, атомы, USE и resolver flags выбираются по пакету и
указываются там, где влияют на результат. Сочетание Portage Manifest и
точного resolver допустимо для metadata gate, если подтверждены его
объём и проверки источников. Общий metadata gate не требует
`pkgcheck` как единственной реализации.

## Политика GitHub

Защита ветки удерживает принятое состояние под контролем владельца.
**Effective settings** — настройки,
фактически применяемые к ветке с учётом rulesets (наборов правил),
legacy branch protection и прав обхода.

### G1

**Применимость.** Все

**Зачем.** Принятые версии определяются явным решением.

**MUST.** Определить default branch, защитить принятое состояние от
неконтролируемых изменений и оставить принятие владельцу.

**Критерий.** Владелец подтверждает целевую ветку, разрешённых участников,
защиту от удаления и неконтролируемого push/force-push, порядок ручного принятия
и его доказательства. Для автоматизации действуют Draft PR и запрет auto-merge
по P4. Для Manual владелец определяет допустимый ручной путь.

### G2

**Применимость.** При выборе или смене required checks, workflow, jobs или
triggers

**Зачем.** Старый или пропущенный check может заблокировать merge или создать
ложный допуск.

**MUST.** Сопоставить каждый требуемый check с реализованной проверкой и её
источником. При изменении согласовать effective rulesets и legacy protection с
workflow, включая approval для automation PR.

**Критерий.** До внедрения согласованы имена контекстов, источники, события и
порядок перехода. На проверочном PR подтверждено появление нужных checks и
блокирование merge при их отсутствии или отказе. Обязательная проверка учитывает
условные шаги и не засчитывает их пропуск.

### G3

**Применимость.** Где GitHub Actions публикует кандидатов

**Зачем.** Запрошенные в YAML права могут расходиться с эффективными
настройками.

**MUST.** Настроить минимальные права Actions по P1 и разрешить создание Draft
PR выбранному механизму публикации.

**Критерий.** Владелец сверяет доступность Actions, политику разрешённых
Actions, токен, право создания PR и порядок одобрения запуска PR-проверок.
Проверка не требует раскрытия значений credentials.

- Default branch SHOULD называться `main`. Краткое описание и релевантные
  topics SHOULD помогать найти оверлей и понять его назначение.
- Проверки, которые владелец выбрал как условие merge, SHOULD быть
  обязательными, если они доступны на нужных PR.
- Dependabot для GitHub Actions SHOULD использоваться там, где владелец
  может ревьюить обновления закреплённых SHA.
- GitHub Pages MAY обслуживать отдельную полезную документацию.
  Генератор сайта и Pages не входят в обязательный baseline.

Для PR, созданного или обновлённого через `GITHUB_TOKEN`, запуски
`pull_request` по `opened`, `synchronize` и `reopened` ожидают
ручного одобрения пользователем с правом записи. Владелец учитывает это
при проверке required checks. [GitHub Docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

## Локальная политика, внедрение и исключения

Оверлей определяет, сколько версий хранить (retention), какие версии
заменять при обновлении (ротация) и как восстанавливаться после отказа.
По этим правилам ревьюер оценивает изменения конкретного пакета.

### L1

**Применимость.** Все, по применимости

**Зачем.** Эти значения зависят от пакетов и определяют безопасный diff и
принятие.

**MUST.** Зафиксировать в оверлее retention и ротацию, откат, генерацию версий,
совместимость нескольких пакетов, USE и зависимости, архитектуры и профили,
provenance, build/runtime сценарии, разрешённые пути публикации и
восстановление.

**Критерий.** Для затронутого пакета ревьюер находит правило, его границы и
способ проверки. Неприменимые пункты имеют ясное основание.

### L2

**Применимость.** При отклонении от применимого требования

**Зачем.** Отклонение должно оставаться видимым при принятии следующего
обновления.

**MUST.** Для альтернативы SHOULD записать причину. Для отклонения от MUST
получить явное решение владельца с указанием требования, области, причины,
доказательств, компенсирующей меры и условия повторного ревью.

**Критерий.** По записи понятно, что действует, для каких пакетов и до какого
пересмотра. Исключение не засчитывается как выполненный MUST. P1–P4 и контроль
владельца из G1 сохраняются.

При внедрении по S2 владелец сверяет точную ревизию с профилем и общими
требованиями, определяет применимые проверки, устраняет разрывы или
согласует допустимые исключения, затем фиксирует решение. Существующие
имена, структура и инструменты допустимы при выполнении контракта.
Новые требования оцениваются при внедрении.
